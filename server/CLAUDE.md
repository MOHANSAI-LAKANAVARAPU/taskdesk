# TaskDesk

Task assignment and tracking web app for managers, team leads and employees. Deployed on the company server (Docker or plain Node).

## Working rules

- **Keep it simple.** No new frameworks or build tools unless the owner asks.
- **Every permission check is enforced in `server.js`**, not only hidden in the UI. The frontend hiding a button is convenience, never security.
- **Escape all user text in the frontend** with the `esc()` helper in `public/app.js` before putting it in `innerHTML` (names, emails, titles, descriptions, messages, project names, attribute values).
- **Database changes must be safe for an existing database.** (Additive-only changes since then, e.g. teams/requests/files in 1.0.7, with a backup in `../backups/taskdesk-before-teams-2026-10-26.*`. One exception was done with care: `db.js` rebuilds the `tasks` table once at startup to allow status `submitted` — snapshot first, one transaction, row count checked, only if the old CHECK is still there. Snapshots: `data/taskdesk-before-approval-migration.db` and `../backups/taskdesk-before-approval-2026-10-26.*`.) Add columns with `ALTER TABLE ... ADD COLUMN` (guarded so it only runs once, e.g. check `PRAGMA table_info`), use `CREATE TABLE/INDEX IF NOT EXISTS`, and never drop tables/columns or delete data.
- **After every change, tell the owner which files changed and how to test it.**
- **Never send real emails during tests.** Any test that can trigger an email (welcome, forgot password, or any notification — real users such as the admin may have their switches on, and managers/admins can approve everything) runs with the server in dry-run mode, then the server is put back:
  - Before: a compose override file outside the repo (e.g. `dryrun.yml` with `services: { taskdesk: { environment: { EMAIL_DRY_RUN: "1", EMAIL_OUTBOX: /tmp/outbox.jsonl } } }`), then `docker compose -f docker-compose.yml -f <dryrun.yml> up -d`. The log must say `[email] ready: … (dry run)`; emails are then only recorded (`/tmp/outbox.jsonl` in the container), never sent.
  - After: `docker compose up -d` (no override). The log must say `[email] ready: …` without "(dry run)". Check `docker logs taskdesk | grep "\[email\] sent"` shows nothing from the test window.
  - Only "Send test email" to the owner's own address is sent for real, and only when the owner asked for it.

## Architecture

- **Backend:** Node.js (>=18) + Express 4. [server.js](server.js) holds all routes, auth and permission logic. [db.js](db.js) opens SQLite (better-sqlite3, WAL, foreign keys ON), creates tables with `CREATE TABLE IF NOT EXISTS`, and seeds the first admin when the `users` table is empty.
- **Auth:** bcryptjs password hashes (people added with a welcome email get an unusable random hash until they use their link); server-side sessions in the `sessions` table; random 32-byte token in an httpOnly, SameSite=Lax cookie `sid` (30 days; `Secure` when `COOKIE_SECURE=true`). Login is rate limited in memory (10 attempts / 15 min per IP). Changing or resetting a password invalidates other sessions; deactivating a user deletes their sessions.
- **Frontend:** plain HTML/CSS/JS single-page app in [public/](public) ([index.html](public/index.html), [styles.css](public/styles.css), [app.js](public/app.js)). No frameworks, no build step. Hash routing: `#/` (dashboard), `#/tasks` (filters via query: `status`, `project`, `assignee`, `mine`), `#/tasks/:id`, `#/projects`, `#/teams` (`?view=people` = "All people", managers/admins; team managers get "People in your teams"), `#/teams/:id`, `#/requests`, `#/requests/:id`, `#/chat`, `#/chat/:id`, `#/history`, `#/account`, `#/login`, `#/forgot`, `#/set-password?token=…` (the last three work signed out). `#/my-team` (old) redirects to `#/teams`; `#/people` (old) to `#/teams?view=people` for managers/admins and `#/teams` for everyone else. `app.js` is one IIFE with a `router()` that calls a `viewXxx()` function per page; `api()` wraps `fetch('/api' + path)` and throws on errors.
- **Static/SPA:** `express.static(public)`; unknown `/api/*` returns JSON 404; any other GET returns `index.html`. `.html`, `.js` and `.css` (and the SPA fallback) are sent with `Cache-Control: no-cache`, so updates show up on the next load.
- **Deployment:** [Dockerfile](Dockerfile) (node:20-bookworm-slim, `npm ci --omit=dev`), [docker-compose.yml](docker-compose.yml) (port 3000, `./data` and `./updates` volumes, TZ/COOKIE_SECURE; the admin account and the email settings come from the untracked `.env` via `env_file`, see `.env.example`). [mailer.js](mailer.js) sends email (see "Email"). [README.md](README.md) has deployment, Nginx, backup notes.
- **Data:** SQLite file at `data/taskdesk.db` (or `$DATA_DIR`). Uploaded files in `data/uploads/` (random names; back this folder up together with the database).
- **Automatic backups:** [scripts/backup.sh](scripts/backup.sh) runs from the user's crontab at 13:00 and 18:00. It takes an online SQLite backup through the running container (`better-sqlite3` `db.backup`, so the server keeps running) plus `data/uploads/` into `~/TaskDesk-backups/YYYY-MM-DD/` (outside the project; a second run the same day replaces that day). It verifies the copy read-only (integrity, foreign keys, row counts, every `files.stored_name` present), keeps the newest 14 days and logs to `~/TaskDesk-backups/backup.log`. A day the laptop is off at both times has no backup. Restore steps (no sudo; the current data is moved aside, never deleted): [scripts/restore.md](scripts/restore.md).

### Page width and grids
- The page (`.wrap`) and the top bar (`.topbar-inner`) share `--page-w` = `min(1800px, 100% − 2 × gutter)`. The gutter is `clamp(0px, (100vw − 1100px) × .075, 2.5vw)`, so it is 0 up to 1100px wide (exactly the old full-width layout on phones and small windows) and grows smoothly to 2.5vw (95vw content) by about 1600px. Content is 1800px from about 1900px wide.
- Grids use `auto-fill` / `auto-fit` with `minmax(min(100%, N), 1fr)`, no fixed pixel layouts:
  - team blocks (`.team-grid`, ~300px cards: 1 on phones, 3 at 1024px, 4 at 1366–1600px, 5 at 1920px+);
  - dashboard sections (`.dash-grid`, ~440px: 1, 2, then 3 columns from 1500px). The Employees table needs ~640px, so it gets a `minmax(640px, 1.2fr)` first column from 1500px and the full row below that (`:has(> .emp-card)`);
  - the board's four columns stretch.
- Wide tables stay in `.table-wrap` and scroll inside it on narrow windows (History needs ~1700px).
- Long text keeps a readable line length: `.desc` and timeline notes `max-width: 85ch`, chat messages `min(85ch, 88%)`. The chat sidebar is `clamp(320px, 20vw, 400px)`.

## Roles and permissions (enforced in server.js)

**Managers and admins have full access to tasks and requests**: they can approve/send back any submitted task (their own too, logged as "Self-approved by <name>"), complete their own tasks directly, take any open request for any team, assign a request to any active person, and edit/reassign/delete any task at any status (deleting a task that delivered a request stays refused). Only admins can create, edit or deactivate admin accounts or grant the admin role. Team leads and employees follow the rules below.

Roles: `admin`, `manager` (shown as "Manager (all teams)": the company manager), `team_manager` ("Team manager": only the teams in `team_managers`), `lead`, `employee`. `isBoss(u)` = admin or manager; `isTM(u)` = team_manager. `users.role` has **no CHECK constraint**: `ROLES` in server.js is the only list of valid roles and every write (`POST`/`PATCH /api/users`) checks it (the first-admin seed in db.js always writes `admin`).

| Capability | admin | manager | team_manager (in the teams they manage) | lead | employee |
|---|---|---|---|---|---|
| See tasks (`taskScope`) | all | all | as a lead of those teams | own tasks, tasks they assigned, tasks of members of teams they lead, tasks linked to their teams' requests | own tasks only |
| See users (`GET /api/users`) | all | all | self + members, leads and team managers of their teams (`?pool=no_team`: active leads/employees without a team, for Add member) | self + members of teams they lead | self |
| Add/edit people, reset passwords, activate/deactivate | yes | yes (cannot create/grant/edit admins) | no | no | no |
| Create/edit projects | yes | yes | no | no | no |
| List projects | yes (counts limited to visible tasks for non-bosses) | yes | yes | yes | yes |
| Assign (create) tasks | to any active user | to any active user | active members of their teams, or self | active members of teams they lead (not team managers), or self | no |
| See teams and their members (name, role, email) | yes | yes | yes (directory) | yes | yes |
| See open task/request counts of a team | yes | yes | their teams | teams they lead | no |
| Create/rename/delete teams, connections, choose team managers | yes | yes | no | no | no |
| Add/remove members, set leads | yes | yes | their teams: only leads/employees without a team or from their teams; leads = team leads from their teams | no | no |
| Restore / delete permanently archived items (History) | yes | yes | items of their teams | no | no |
| Edit/delete a task (`canEditTask`) | any | any | as a lead | only tasks they assigned | no |
| Self-claimed request task (assigned_by = assignee) | edit/delete (any status) | edit/delete (any status) | as a lead | edit/delete if a lead of the request's team; the claimer can't edit/delete, only "Give back" | claimer: "Give back" only |
| Post progress update / change status | any visible task | any visible task | as a lead | tasks they are assignee of or assigned | only tasks assigned to them |

**Team managers (`team_managers`).** A person with role `team_manager` manages one or more teams (chosen by managers/admins in the person form, "Manages teams" picker, or on the team page's "Team managers" section → `PUT /api/teams/:id/managers`). They usually belong to one of them but don't have to. **Inside those teams they have everything a lead has**: the SQL `LED_TEAMS` and the JS `runsTeam(u, teamId)` mean "teams the user leads *or manages*" (the `team_powers` TEMP view in db.js = `team_leads` ∪ `team_managers`; it lives only in the connection, nothing is stored), so every lead scope (tasks, requests, History/CSV, dashboard, team counts, my-summary/desktop badge and notifications, "still unassigned" emails, team chats) covers managed teams. `isLeadOf`/`leadsOf` stay "real leads only" (labels, `nobodyCanApprove` wording); `managesTeam`/`managersOf` are the team-manager versions. Outside their teams a team manager is like an employee (they still send requests to their own and connected teams, `allowedTargetTeams`). They can't create/rename/delete teams, change connections, create or edit people (incl. managers, team managers, admins), route "needs a team" requests, delete (archive) requests, or open Email settings and Remove person. Their `team_managers` rows are deleted when their role changes or they are deactivated or removed; a person who becomes a team manager loses their `team_leads` rows (they already have lead powers). Becoming a team manager needs at least one team.
- **Their own work is never approved by themselves or by their team's leads**: `isTMWork(assigneeId)` limits the team part of `canReviewTask`/`reviewScope`/`approversFor` to *other team managers* of that team, plus the assigner and managers/admins. Leads therefore can't assign tasks or requests to a team manager (`canAssignTo`, `/assign`); another team manager of the team can. `nobodyCanApprove` says "a team manager's work is approved by another team manager of <team> or a manager".

**Teams replace "Reports to". Several leads per team, all equal.** A team's leads are the rows of `team_leads` (each must be an active lead/manager/admin; their rows are removed automatically if they become an employee or are deactivated). **Every check is "any lead of the team"** — `LED_TEAMS` (SQL: teams the user leads), `isLeadOf(u, teamId)`, `leadsOf(teamId)`; never compare with a single lead. `teams.lead_id` stays in the database only for compatibility: `syncLegacyLead()` keeps it equal to the first lead (by `added_at`), and no check reads it. Each user has one `team_id`. `users.lead_id` stays in the database but is no longer used. A person may lead several teams, and may lead a team they aren't a member of (e.g. Sumit leads R&D).

**Teams page (everyone).** `#/teams` is a grid of team blocks (3 columns wide, 1 on phones): name, "Lead: X" or "Leads: X, Y" (managers see "⚠ No lead" when there is none), active members, and for the team's leads and managers/admins the open tasks and open requests; the user's own team comes first ("Your team"). `#/teams/:id`: the leads (marked "not a member of this team" where so) and members (name, role, email; every lead marked "Lead"). Each lead also sees each member's open task count and "Assign a task" (opens the task form with that person picked); managers/admins also get Add member (type-to-search), Remove, **Leads** (multi-person type-to-search picker with chips: active leads/managers/admins, marked "already leads <team>" → `PUT /api/teams/:id/leads {user_ids}`, which replaces the list), Rename and Delete.

**Auto-lead (`autoLead`).** When an active user with role `lead` joins a team — `POST /api/users` with a team, `PATCH /api/users/:id` that changes their team (or changes their role to lead while in a team), or `PUT /api/teams/:id/members/:userId` that moves them into it — they are added as one of its leads (even if it already has leads); the response carries `became_lead: { team_id, team_name, name }` and the UI shows "<name> is now a lead of <team>". It runs **only when the team actually changed or the role became lead**: saving a name/email, the same role, or re-adding someone to the team they're already in never re-adds a lead a manager removed. The "All people" view of the Teams page shows "Lead of <team>, <team>" under the role, and "⚠ Not leading a team yet – set it on the Teams page" for an active role-`lead` user who leads no team.

**Team connections (1.0.12).** `team_connections` links two teams that work together (two-way, one row per pair, smaller id first). Managers/admins tick them on the team page ("Connected teams" checkboxes → `PUT /api/teams/:id/connections {team_ids}`, which replaces the team's whole list); everyone sees the list on the team page and "Works with: …" on the team blocks. Nothing is seeded: until a manager connects teams, employees can request only from their own team (or "Not sure").

**Remove person (admins only, never their own account, never the owner or a protected account).** In Teams → All people and in the person Edit form. `GET /api/users/:id/removal` counts the person's records (`personRecords`: tasks as assignee, tasks they assigned, approvals, requests, task updates + request activity, files, chat messages, and other references — deleted-by, asked/withdrawn requests, projects/chats/team links/lead roles they created) plus the teams they lead; the dialog shows them. `DELETE /api/users/:id`:
- **No records** → the user row is deleted (sessions, chat memberships and mutes, lead roles go with it by cascade).
- **Records** → the row stays for History: `removed_at`/`removed_by` set, `active = 0`, sessions ended, `team_id` cleared, lead roles removed (`syncLegacyLead`), removed from group and team chats (direct chats stay readable for the other person), `original_email` = their email and `email` = `removed-<id>@removed.local` (so the address can be used for a new account), and `name` gets " (removed)" — so every place that shows the name (History, CSV, tasks, requests, chat) shows "<name> (removed)".
- Removed people are left out of `GET /api/users` (so All people, pickers, filters) unless managers/admins ask for `?removed=1` (All people → status "Removed"); they have no team and are inactive, so they're also out of team members, leads, New chat, assignment and ask-a-person lists. They can't be edited or added to a team (409/404) until restored.
- `POST /api/users/:id/restore` (admins): only if `original_email` isn't used by another account (409 otherwise); reactivates the account, puts the email and name back, and does **not** give back teams or lead roles.

Other rules: a user cannot deactivate themself; only admins can create admins or modify admin accounts. Deadlines/start dates are `YYYY-MM-DD`.

**Password rules (Security A1, `passwordProblem`)** apply wherever a password is set: Account → Change password (`POST /api/me/password`), set-password links from the welcome email and "Forgot password?" (`POST /api/password/set`), and passwords a manager types (`POST /api/users`, `PATCH /api/users/:id`). Existing passwords keep working; only new ones are checked. A refused password leaves a set-password link usable.
- At least 10 characters (at most 200).
- Not a common password: `common-passwords.txt` holds the top 1000 of the SecLists "10k most common" list, plus its 51 entries of 10+ characters, since the length rule already stops every top-1000 one. Also refused: such a password with digits or symbols around it (`password123!`, `2024monkey!!`), the same one twice (`dragondragon`), and one repeated character.
- It can't contain the person's email name: the part before `@` (and before `+`) if it has 3+ characters, or a 4+ character piece of it split at `.`, `_` or `-`.

**Sign-in lockout (Security A1).** 8 failed sign-ins for one email within 15 minutes lock it for 15 minutes. While locked, even the right password gets 429 "Too many attempts. Try again in 15 minutes or use Forgot password."
- It is stored in the database (`login_failures`, `login_locks`, keyed by the lowercased email, also for unknown emails, so nothing reveals whether an account exists), so a restart doesn't unlock.
- A successful sign-in clears the failures; using a set-password link (welcome / Forgot password) lifts the lock.
- The older per-IP limit (in memory: more than 10 attempts from one address in 15 minutes → "Too many sign-in attempts…") is checked first and unchanged.

**Sessions (Security A1).** A session ends after **8 hours without activity** (`IDLE_HOURS`, `sessions.last_active_at`, written at most once a minute) with 401 "You were signed out after 8 hours without activity…", besides the 30-day limit.
- Background calls never count as activity: the desktop app's `/api/my-summary` and `/api/stream` (by path, so the desktop app needs no change), and web-app refreshes sent with `X-Background: 1` (`api(path, { background: true })`: the chat list and unread count, the polling fallback, reloading the open chat after a live event, and automatic "mark as read").
- The stream's 25-second ping also ends idle sessions.
- Sessions from before this change get a value on their first request.
- Account page → "Signed-in devices": `GET /api/me/sessions` counts other live sessions (other browsers; the desktop app is one), and "Sign out all other devices" (`POST /api/me/sessions/sign-out-others`) ends them.
- A password change ends the other sessions (Account page) or all of them (a manager setting it, set-password links).

**Owner and protected accounts** (backup `../backups/taskdesk-before-owner-2026-10-29.*`):

The owner:
- **Who.** The owner is set on the server only: `OWNER_EMAIL` in `server/.env` (Mohan Sai). It is resolved once at startup to `ownerId`, and only if it matches an **active, non-removed admin** (any letter case). Otherwise the server logs `[owner] WARNING: … nobody is treated as owner` and the normal admin rules apply, so nobody is ever locked out.
- **Who can change it.** Nobody but the owner can change the owner's account in any way, admins included. Every attempt gets 403 "This account can't be changed." (`ownerRefused`) and is recorded on the owner.
- **Guarded endpoints.**
  - `ownerFirst(...)` runs before `requireBoss`/`requireAdmin`, so even a lead or employee gets the owner message on: `PATCH /api/users/:id` (any field), `POST /api/users/:id/welcome`, `GET /api/users/:id/removal`, `DELETE /api/users/:id`, `POST /api/users/:id/restore`.
  - On `PUT`/`DELETE /api/teams/:id/members/:userId` (`memberTarget`) the check comes after the team-power check.
  - `PUT /api/teams/:id/leads`: when the owner would be added or dropped as a lead.
  - `PUT /api/teams/:id/managers`: when the owner is in the change.
  - `DELETE /api/teams/:id`: when the owner is a member, because deleting the team would change the owner's team.
  - Sessions and password links are only touched by those endpoints (password, deactivate, remove, welcome), so they are covered.
  - "Forgot password?" stays open; the link only goes to the owner's own inbox.
- **On their own account,** the owner may change name, team, lead and password (`PATCH` and the team page, including their own lead role).
  - Changing their role, deactivating or removing themself → 403 "This account can't be removed, deactivated or given a lower role."
  - Changing their email → 403 "Role and email are fixed for this account.", because it must stay equal to `OWNER_EMAIL`.
  - Turning off their own protection → 403.
- **Transfer.** Ownership moves only with [scripts/transfer-owner.sh](scripts/transfer-owner.sh) `<email of an active admin>`, which needs access to this computer. There is no API or UI. The script checks the person (read-only, through the container), keeps `.env.bak-<time>`, changes only the `OWNER_EMAIL` line, recreates the container and appends to `server/owner-transfers.log` (git-ignored, like `.env.bak-*`). Test overrides: `ENV_FILE`, `CHECK_DB`, `RESTART_CMD`, `LOG_FILE`. Recovery steps: [scripts/restore.md](scripts/restore.md), "If the owner leaves or is locked out".
- **Recording a change of owner.** At startup the server compares the owner with `app_settings.owner_user_id`. If it changed (first setup, a transfer, or `OWNER_EMAIL` no longer matching), it records an `owner_transfer` event on the people concerned and stores the new id.

Protected accounts:
- **Which accounts.** `users.protected = 1`, and **the owner, always** (`isProtected`). Deepith Jain was protected once, by the migration that added the column.
- **What is blocked.** A protected account can't be removed (`/removal`, `DELETE`), deactivated (`active: false`), or given a lower role (`ROLE_RANK`: admin 5 > manager 4 > team_manager 3 > lead 2 > employee 1), by anyone. The message is "This account is protected. It can't be removed, deactivated or given a lower role.", and the refusal is recorded.
- **What still works.** Admins can still change its name, email, team and leads, reset its password, resend the welcome email, and raise its role.
- **Turning it on or off.** Only the owner can, with `protected` in `PATCH`; anyone else gets 403 "You can't turn protection on or off." and the attempt is recorded. The owner's own protection can't be turned off ("This account is always protected."). Each change is recorded as `protection_on` / `protection_off`.

The page (**the owner is never labelled**):
- **No "owner" anywhere people can see.** Nothing in the web app, its served files (`app.js`, `styles.css`) or any message other users can get says "owner". "Owner" wording stays only in server logs, `account_events`, this file and `scripts/restore.md`.
- **Badges.** `publicUser` and team members carry `locked` (the owner; a neutral name on purpose) and `protected`, which is the stored `users.protected` flag only, so the owner shows as unprotected and their row looks like a normal admin row. The page shows "🔒 Protected" next to the role for other protected people (All people, team member lists, Account page). The enforcement still uses `isOwner` / `isProtected` on the server.
- **Hidden controls.** For everyone but the owner, the `locked` row has no Edit and no Remove / Remove person, and isn't offered in "Add member". Protected people have no Active switch and no Remove person. Their role list only offers the same or higher roles, with a note.
- **The owner's own form** has the role locked and the email read-only, with the note "Role and email are fixed for this account."
- **The owner sees a "🔒 Protected account" checkbox** on other people's forms. Unticking it asks "Turn off protection for <name>?"; if they cancel, nothing is saved.
- **Account history.** Managers/admins see "Account history" in the person form (`GET /api/users/:id/events`). The API never returns `owner_transfer` events, and returns `owner_refused` only to the owner. Both stay in the table.

**No performance scores.** The dashboard shows only counts: tasks assigned (total), completed, in progress, not started, overdue — overall, per project and per employee — plus tasks due in 7 days and completed in the last 7 days. Do not add ratings/scores/rankings.

Task status values: `assigned` (shown as "Not started"), `in_progress`, `submitted` (shown as "Waiting for approval"), `completed`. "Overdue" is derived (`status != completed` and `deadline < today`), not stored.

**Approval step (enforced in server.js, not just the UI):**
- Assignees can't mark a task Completed. They use `POST /api/tasks/:id/submit` with a required `note` → status `submitted`, `submitted_at` set. While `submitted`, the assignee (and everyone) can only add comments via `/updates`; status/progress changes return 409. `status: "submitted"` can't be set through `/updates`.
- Reviewers (`canReviewTask`): any manager/admin; the person in `assigned_by` when that isn't the assignee; and when that person is a lead of the assignee's team, **any lead of that team** (`assignerLeads(task)`; tasks a manager assigned stay with that manager and other managers); for a **self-claimed document request** (`assigned_by` = assignee, task linked to a request) any lead of the request's target team other than the assignee (so a lead who takes a request is approved by another lead of the team or a manager). Nobody else (leads of other teams can't). Leads/employees never approve their own task; a manager/admin may, and it is logged as "Self-approved by <name>" (approved_by = themselves) and shown as "(self-approved)" in History/CSV. `POST /api/tasks/:id/approve` (optional `note`) → `completed`, progress 100, `completed_at` = now, `approved_by` = reviewer. `POST /api/tasks/:id/send-back` (required `reason`) → `in_progress`, `submitted_at` cleared. Both write to the task's activity timeline ("Approved: …", "Sent back: …").
- `approversFor()` lists who can actually approve (same rules, active users only, never the assignee): the assigner (plus the team's other leads when the assigner leads the assignee's team), or for a self-claimed or person request every lead of the team except the assignee and the requester, plus "any manager" if another active manager/admin exists — shown as "Waiting for approval from A, B or any manager"; `self` is true when the assignee is a manager/admin (they can approve it themselves, so the block below never applies to them). The task page shows "Waiting for approval from …" from this. If nobody but the assignee could approve, "Take this task", "Assign to" (to oneself) and "Submit for approval" are refused with "Nobody can approve this yet. Ask a manager to set a lead for <team>." (`nobodyCanApprove(request, assigneeId)`; other leads of the team count as approvers; when the assignee is one of the team's leads and there's no other lead or manager, it says "…work a lead of <team> takes is approved by another lead of the team or a manager. Ask a manager to add another lead." instead). The Teams page warns on teams without a lead.
- A plain task someone assigned to themself (`ownPlainTask`: `assigned_by` = assignee and no linked request) is completed directly via `/updates` (no approval; `submit` is refused). A self-claimed request task must be submitted. The assigner or a manager/admin may complete someone else's task directly via `/updates` (recorded as `approved_by`); a manager/admin may also complete their own task directly (logged as self-approved); nobody else can. An assignee can't move an approved task back out of Completed.
- Reassigning a submitted task resets it to `in_progress` with a note "Moved back to in progress for <name>". Reassigning a self-claimed request task makes the person reassigning its `assigned_by` (so the old claimer doesn't become its approver).
- Only `completed` tasks count as completed in dashboard totals, per-project and per-employee numbers; `submitted` is counted separately (`totals.submitted`, per person). `GET /api/dashboard` also returns `awaiting_me` (submitted tasks the current user may approve).
- Task detail returns `can_submit`, `can_review`, `can_complete_directly`, `locked`.

### Document requests

- **Who can request from whom (`allowedTargetTeams`)**: a user may send a request to their own team and to teams connected to it; managers/admins to any team; a user without a team only "Not sure, let a manager decide". Enforced on `POST /api/requests` (403 otherwise). "Send to team" is managers/admins only, so it is never restricted. `GET /api/request-targets` gives the New request form its allowed `teams` and askable `people`.
- **Visibility (`canSeeRequest` / `requestScope`)**: a request is visible only to managers/admins, the requester, members and leads of the requester's team (the requester's current team), members and leads of the target team, the assignee of its task, and the person it was withdrawn from. Everyone else gets 404 and doesn't see it on the board, in History or the CSV; attachments and delivered files follow the same rule.
- **Ask a person** ("Send to: ○ A team ○ A person"): `POST /api/requests` with `person_id` (an active member of the requester's own or a connected team; managers/admins: anyone in a team; never yourself, never someone without a team). It is created already `assigned`: a linked task (assignee = the person, `assigned_by` = the requester, deadline = needed-by), `target_team_id` = the person's team, `requests.asked_person_id` = the person, and the activity "Sent to <person> by <name>". Approved by any lead of the person's team or a manager/admin — **never by the requester** (also not when the requester leads that team; the other leads can) (even a manager requester), and not by the person unless they are a manager/admin; the requester can't edit or complete it directly either. The person can "Give back" (request returns `open` to the team's board, `asked_person_id` cleared, so it is an ordinary team request again). If a lead reassigns it, that lead becomes its `assigned_by` and `asked_person_id` is cleared. Approved → `delivered` and the requester is told as usual. A lead still can't assign tasks directly to people outside the teams they lead.
- **Withdraw** (`POST /api/requests/:id/withdraw`, requester only): an `assigned` request (person or team) whose task is still `assigned`/`in_progress`. Archives the linked task (see "Archive instead of delete"), sets the request `cancelled` (`closed_at`, `withdrawn_from_id` = who had it), logs "<requester> withdrew the request". Refused once the work is submitted or delivered. Open requests are cancelled with "Cancel request" instead.
- Status (validated in server.js, **no CHECK constraint**, so adding a status needs no table rebuild): `needs_team` (posted with "Not sure, let a manager decide", no `target_team_id`; nobody can take/assign it; a manager/admin uses "Send to team" → `POST /api/requests/:id/send-to-team {team_id}`, which sets the team, makes it `open` and logs "Sent to <team> by <name>" in `request_events`) → `open` → `assigned` (linked task created) → `delivered` (linked task approved/completed) → `closed` (requester clicks "Mark as received"). `cancelled`: requester or manager/admin, only while `needs_team` or `open`. History shows team "Not decided yet" for `needs_team`.
- "Take this task" (`canTakeRequest`): any active member of the target team, any of the team's leads (even if not a member of it), or any manager/admin (any team) claims an open request → linked task with assignee = assigned_by = them (approved by a lead of the team other than them, or a manager). "Assign to": managers/admins and any lead of the target team pick an active team member (managers/admins: any active person, list grouped by team), or themself (same as taking it) → linked task with assigned_by = the person who clicked. Claims are atomic (`WHERE status = 'open'`): when two leads act at once, one wins and the other gets 409 "Already assigned to <name> by <lead>." ("Already taken by <name>." if the winner took it themself; `takenMessage()`), also when the request was taken before they clicked.
- "Assign to" on an open request (the target team's leads and managers/admins) is a single-person type-to-search picker: a lead sees the team's active members, managers/admins everyone (the request's team first). When they may take it, the current user is listed first as "<name> (me)" and choosing it calls `/take` (opens their new task). A lead's own work is approved by another lead of the team or a manager/admin, never by themself. With nobody else in the team it says "No other members in <team> yet – add them on the Teams page".
- Dashboard "Requests to assign" (`to_assign` in `GET /api/dashboard`): open requests for teams the user leads; managers/admins: all open ones plus `needs_team` ("Choose team"). "Assign" opens the same picker in a dialog.
- Reminder: `remindStaleRequests()` runs on every `GET /api/my-summary` and sets `requests.reminded_at` (once, never reset) on requests still `open` 24 hours after they became open (the later of `created_at` and the latest `request_events` entry, i.e. "Sent to team" or "gave back"). Flagged open requests are returned as `unassigned_reminders` to every lead of the team and to managers/admins.
- "Give back" (`POST /api/tasks/:id/give-back`): the claimer of a self-claimed request task (or the person a request was sent to with "Ask a person"), only while the task is `assigned`/`in_progress`, archives the task, sets the request back to `open` and logs "<name> gave the request back" in `request_events`. The team is notified again because the request reappears among open `team_requests` (the desktop app sees it as new if it polled while the request was taken, i.e. after about a minute).
- Reopening a completed linked task moves the request back to `assigned`; deleting the linked task of an `assigned` request puts it back to `open`; deleting the task of a delivered/closed request is refused.

### Archive instead of delete
- Nothing is removed by everyday actions. "Delete" on a task (same permission as before: `canEditTask`), "Give back" and "Withdraw" call `archiveTask()`: they set `tasks.deleted_at`/`deleted_by` (and `archived_request_id` = the request it was linked to); the row, its updates and its files stay (files stay on disk).
- Managers/admins can also "Delete" a request (`DELETE /api/requests/:id`) while nobody is working on it (`needs_team`, `open`, `cancelled`, `closed`); it sets `requests.deleted_at`/`deleted_by` and logs "<name> deleted the request".
- Archived rows are hidden everywhere live: task lists and task pages (404), dashboard, team counts, approvals, requests board and request page (404; actions on it too), `my-summary` (so the desktop badge and notifications). `taskScope(u, archived)`, `requestScope(u, archived)` and `getRequest` (live) vs `getAnyRequest` do the filtering; any new query on `tasks` or `requests` must add `deleted_at IS NULL`.
- History (and its CSV) still lists them, to the same people as before, with status `deleted` ("Deleted", also a status filter) and "Deleted by <name> on <date>" (CSV column "Deleted"). The title is not a link.
- Managers/admins, and team managers for their teams' items (`canManageArchived`: a task's team is its assignee's team, a request's team its target team; History rows carry `can_restore`), get "Restore" and "Delete permanently" (confirmation) on those History rows:
  - `POST /api/tasks/:id/restore`: clears the archive. A task that came from a request goes back on it only if the request is still waiting for it — `open` again (after a delete or give back), or `cancelled` by a withdraw from this same person — and the request becomes `assigned` again (a person request again if it was one; "Restored by <name>: <person> has it again"). If someone else took the request, it was finished, or the request is archived, restore is refused (409).
  - `POST /api/requests/:id/restore`: clears the archive ("Restored by <name>").
  - `DELETE /api/tasks/:id/permanent` / `DELETE /api/requests/:id/permanent`: only for archived rows; removes the row with its updates/activity and file rows (cascade) and deletes the stored files. A request's linked task, if any, is kept. Shared assignment files are only deleted once no other copy links to them.

### Chat (1.0.14)
- **Privacy:** only members of a conversation can read it, its files and its search hits — **admins and managers included**. Every chat endpoint starts with `chatMember(u, id)` (no membership → 404), and `GET /api/files/:id` for a chat file checks membership too. Don't add a "boss sees everything" shortcut here.
- Types: `direct` (one per pair of people; found or created inside a transaction by `POST /api/chat/direct`), `group` (name + people; managed by its group admins, see "Group admins" below; anyone can leave), `team` (one per team, kept in sync by `syncTeamChats()`: members = the team's active members plus all its leads and team managers, even those who aren't members; it runs at startup and after every change to users, teams, team members and leads; a rename of the team renames the chat). People added later see the history, but it doesn't count as unread (their `last_read_message_id` starts at the latest message). Someone removed loses access completely. Deactivated people leave team chats but stay in direct/group chats.
- Deleting a team archives its chat (`conversations.archived_at`, name gets " (team deleted)"): its members can still read it, nobody can post (409).
- Messages: text up to 5000 characters and/or up to 5 files (same upload rules as everywhere: `withUploads`, any type, `MAX_UPLOAD_MB` each; membership is checked before the upload is parsed). Files are `files` rows with `message_id`. A sender can delete their own message: `deleted_at` is set, the API no longer returns its text or files ("This message was deleted"), the files return 404 but stay on disk (archive-not-delete). No editing yet (`edited_at` is unused).
- Unread = messages after the member's `last_read_message_id`, not deleted, not their own. `chatUnreadTotal()` (menu count, desktop badge, `chat_unread` in my-summary) leaves out muted chats. `POST /api/chat/:id/read` only moves forward. The page marks a chat read only while it is open, the page is visible and the window focused.
- Mute (`conversation_members.muted`, "Mute" in the chat header): no desktop notifications and not counted in the badge; stored on the server, so it applies on every device.
- Images: `GET /api/files/:id?inline=1` sends PNG/JPG/GIF/WEBP **chat** images inline (thumbnails, lightbox) with `nosniff` and `Content-Security-Policy: sandbox`; everything else is always an attachment.
- Search (`GET /api/chat/search?q=`, 2+ characters): message text and file names, only in the user's own conversations, deleted messages left out; `LIKE` with `%`/`_` escaped.
- **Live updates:** `GET /api/stream` (Server-Sent Events, session cookie) keeps an in-memory `Map<userId, Set<res>>` (max 10 per user; a ping every 25 s also ends the stream when the session is gone). `push(userIds, event, data)` sends `message` (`conversation_id`, `conversation_name` as the receiver sees it, `type`, `muted` = the receiver's setting, `unread_total`, `message`), `deleted`, `read` (to the reader's own pages/apps only) and `conversation` (created/renamed/members changed; also to people just removed). The page uses `EventSource`; while it isn't open it polls `GET /api/chat` and `GET /api/chat/:id/messages?after=<id>` every 10 s. Behind Nginx, `/api/stream` needs `proxy_buffering off` (the server also sends `X-Accel-Buffering: no`) and a long `proxy_read_timeout` (see README).
- **Group admins** (group chats only; backup `../backups/taskdesk-before-group-admins-2026-10-29.*`):
  - **Who** (`groupAdminReason(c, userId)` → `creator` / `role` / `made`):
    - the creator (`conversations.created_by`);
    - every member whose role is admin, manager, team_manager or lead (`AUTO_ADMIN_ROLES`, from their current role);
    - members another group admin made one (`conversation_members.is_admin`).
  - **What they can do** (`canManageChat`, also needs the chat not archived): add active people (type-to-search, with the note "They'll be able to see earlier messages in this group."), remove members, rename the group, and make any member a group admin (`PUT /api/chat/:id/admins/:userId`).
  - **Removing someone** (`canRemoveChatMember`):
    - the creator only by a company manager/admin (`isBoss`);
    - another group admin (by role or made one) only by the creator or a company manager/admin;
    - plain members by any group admin.
  - **Taking away admin rights** that were given (`DELETE /api/chat/:id/admins/:userId`, `canUnmakeChatAdmin`) follows the same rule, and anyone may give up their own. Admins by role or the creator can't be unmade (409).
  - **Employees who aren't group admins** can read, send, mute and leave only. Anyone can leave, the creator included; nobody else can then remove them, since they're gone.
  - **Not affected:** team chats stay automatic (no group admins, `Only groups can be changed.`) and direct chats are unchanged.
  - **The People dialog** shows "Made the group" / "Group admin" and only the buttons the server allows: the per-member `admin`, `can_remove`, `can_make_admin` and `can_unmake_admin` from `GET /api/chat/:id`.
- **System lines** (`messages.system = 1`, `chatSystemLine()`):
  - The lines are "X added Y", "X removed Y", "X made Y a group admin", "X removed Y's group admin rights" and "Y gave up group admin rights". `sender_id` = who did it.
  - They are shown as small centred lines (`system: true` in message views).
  - They are **not messages**: never pushed as a `message` event (so no desktop or browser notification; the change is pushed as a `conversation` event, which reloads the open chat), never unread (`UNREAD`), never the chat-list preview, not in search, and can't be deleted.
- Page: `#/chat` (list: name, last message, time, unread; search; "New chat" picks anyone active via `GET /api/chat/people`, "New group") and `#/chat/:id` (header with Mute/People/Rename/Leave; messages grouped per sender within 5 minutes, "Today"/"Yesterday" separators, links made clickable after escaping; paperclip, drag and drop, pasted images named `pasted-image-<time>.png`; image thumbnails open in a lightbox, other files as a card with Download; 50 messages, older ones load on scroll up). On phones the list and the conversation show one at a time.

### Files

- Uploads with multer (field `files`, multipart) on `POST /api/tasks` (assign), `POST /api/tasks/:id/updates`, `POST /api/tasks/:id/submit`, `POST /api/requests`, `POST /api/requests/:id/files`. (and chat messages). **Any file type** (firmware, source, archives, docs: no allow-list, no `accept=` on file inputs, so the picker shows "All files"); max `MAX_UPLOAD_MB` per file (`.env`, default 50, capped at 2048; multer `fileSize`; too big → 400 "Each file must be 50 MB or smaller."), 5 per request. `/api/me` and `/api/login` return `upload_max_mb` so the page says "Any file type · up to 50 MB each, 5 at a time" and chat refuses bigger files before sending. A reverse proxy in front needs a body limit of at least 5 × `MAX_UPLOAD_MB` (README nginx example). Permission checks run before the upload is parsed; any error response deletes the stored files.
- Stored in `data/uploads/` under random 32-hex names; `files` table keeps the original name; `files.mime` is decided **by content** (`sniffFile`: the first bytes, PNG/JPEG/GIF/WEBP/PDF, everything else `application/octet-stream`), never by the name. `GET /api/files/:id` needs sign-in and the same visibility as the task or request (plus: once a request is delivered, people on that request can download its task's files).
- **Nothing uploaded can run inside TaskDesk:** every download is `Content-Disposition: attachment` with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`; its `Content-Type` comes from sniffing the stored bytes at download time (`image/*` or `application/pdf` only when the content really is one, otherwise `application/octet-stream`), so `.html`, `.svg`, `.js` (or HTML renamed to `.png`) always download. Chat image previews (`?inline=1`, the only inline responses) only for content-checked PNG/JPEG/GIF/WEBP; SVG is never an image.
- Program and script files (`PROGRAM_EXT` in app.js: .exe .msi .bat .cmd .com .scr .ps1 .vbs .js .jar .sh .apk .dll .lnk .hta .appimage .deb .rpm) show "⚠ Program file: only open it if you trust the sender" next to the file in tasks, requests and chat (display only).

### Multi-person assignments (assignment groups)
- Assigning one task to 2+ people (`POST /api/tasks` with several `assignee_ids`) still creates one separate task per person, but all copies get the same `tasks.assignment_group_id` (= the first copy's id; no foreign key, so deleting that copy keeps the group). One person: no group. Tasks from before this change have it empty and are never grouped.
- **Files at creation**: the "Assign a task" form has "Attach files (optional)" (multipart, same uploader and limits). For a group each file is stored **once** (`files` row with no task/request/message) and linked to the first update ("Assigned to <name>") of every copy in `task_files`; for one person it's a normal task file. The role check runs before the upload is parsed; a refused person or a too-big file creates nothing and removes the upload.
- **Send to the whole assignment**: on a grouped copy, someone who may edit it (`canEditTask`: the assigner, the team's leads/team managers when the assigner runs the team, managers/admins) and isn't its assignee sees "Also send to the other N people in this assignment" (ticked by default; `group_send_count` from `GET /api/tasks/:id`). `POST /api/tasks/:id/updates` with `also_group=1` adds the same note to every other **live** (not archived) copy they may also edit (`groupTargets`), as that person, and any files are stored once and linked to each of those updates; the response has `sent_to`. A status/progress change stays on the copy it was made on. An assignee's updates always stay on their own copy (`also_group` is ignored). Each copy that gets the note notifies its own assignee (see "Note notifications" under Email and the desktop app), so a group note is one notification per person.
- **"Part of an assignment to: …"**: `GET /api/tasks/:id` returns `group` = the other live copies the viewer can see (`canSeeTask`), shown as links on the task page; employees normally see none, so the line is hidden for them.
- **Files are shared, not copied**: `GET /api/files/:id` for a shared file is allowed if the person can see any copy it's linked to (`taskFileVisible`, same rules as task files). Archiving a copy keeps its links (the others are unaffected; restore brings it back). `DELETE /api/tasks/:id/permanent` removes that copy's links and deletes a shared file (row and disk) only when no other copy, live or archived, links to it.
- History, counts, approvals and permissions stay per task (each copy is a normal task).

### Email (Zoho)
- [mailer.js](mailer.js) (nodemailer): `host`/`port`/`secure` straight from `.env` (Zoho `smtppro.zoho.com:465` SSL, app-specific password), no auto-detection; sender `TaskDesk <address from SMTP_FROM>`. Email is off when `SMTP_HOST`, `SMTP_USER` or `SMTP_PASS` is missing (adding a person then needs a password).
- **Never blocks the app:** `mailer.queue()` puts the email in an in-memory queue and returns; one worker sends them one at a time, 3 attempts (retry after 1 min, then 5 min). Logged as `[email] sent to …` / `[email] failed (attempt n/3) to …: <reason>` (the password is scrubbed from any text). After the third failure it is the "last error". Emails still waiting are lost if the server restarts. Only "Send test email" sends right away (`sendNow`) so the admin sees the result.
- Reasons: `EAUTH` → "Sign-in failed: check the app password (535)"; connection/DNS/timeout → "Can't reach <host>:<port> (<detail>)"; refused address → "The address was refused: …".
- **Design** (`layout()`): the Hi-Focus banner ([email-banner.jpg](email-banner.jpg), 600×220, cut from `public/branding/hifocus-banner.png`) embedded inline (`cid:`; `APP_URL` is a LAN address, so a linked image wouldn't load outside the office), heading, a line or two, one button (+ the link written out), footer "Sent by TaskDesk, Hi-Focus. Please don't reply to this email."; always a plain-text version too. All text is HTML-escaped. Links are `APP_URL` + `/#/…`. Emails carry titles and names only: **never user files, descriptions or chat text** (one exception the owner asked for: the note email quotes the first 100 characters of the note).
- **Password links** (`password_tokens`): `issueToken()` stores only the SHA-256 of a random 32-byte token and marks the person's earlier unused tokens used; link `APP_URL/#/set-password?token=…` (after the `#`, so it never reaches server logs). Welcome links last 48 h, reset links 1 h; single use. `POST /api/password/set` refuses used/expired tokens and inactive/removed people (410), and in one transaction sets the password, marks all the person's tokens used and **ends all their sessions**. The page takes the token off the address bar (`history.replaceState`).
- **Welcome:** `POST /api/users` without a password (or `send_welcome: true`) creates the account with an unusable random hash and queues "Welcome to TaskDesk" (`sendWelcome(user, by)`, reusable for a future bulk import); a typed password still works (fallback). `POST /api/users/:id/welcome` = "Resend welcome email" in the person Edit form (managers/admins; admin accounts admins only; not for deactivated or removed people); earlier links stop working.
- **Forgot password:** `POST /api/password/forgot` always answers 200 "If that email exists, we've sent a link…" (same for unknown, deactivated and removed accounts — only an active, non-removed account gets an email). In-memory limits: 3 per email and 10 per IP an hour; over the limit nothing is sent, same answer. `GET /api/password/check` and `/set` are limited to 60 per IP per 15 min.
- **Notification emails** (Account → Email notifications; `users.email_*`, all **off** by default; `notifyEmail()` only to active people with the switch on, never to the person who did the action):
  - `email_assigned` "New task: <title>" — a task is created for them (`POST /api/tasks`), a lead/manager assigns them a request (`createRequestTask`, not when someone takes it themself), Ask a person, reassignment (`PATCH /api/tasks/:id`).
  - `email_approval` "Waiting for your approval: <title>" — on submit, to every user with the switch on for whom `canReviewTask` is true (so a manager with it on gets every submission).
  - `email_ready` "Your request is ready: <title>" — when `syncRequestWithTask` delivers the request, to the requester.
  - `email_notes` "New note on: <title>" / "Files added to: <title>" (1.0.16) — someone posts a note and/or files on a task through `POST /api/tasks/:id/updates` (`emailNote`): to the task's assignee, or to the assigner when the assignee posted; never the poster (own self-assigned tasks: nobody). A group note emails each copy's assignee once. The email quotes at most the first 100 characters of the note (then "…") and only says how many files ("with 2 files" / "sent 2 files"), never names or attachments. Status/progress-only updates, submit, approve and send back don't count (they have their own notifications).
  - `email_unassigned` "Still unassigned: <title>" — leads only (refused for anyone who leads no team): when `remindStaleRequests()` flags a request (it now also runs every 10 minutes, and returns the newly flagged ones, so each request is emailed once), to the target team's leads.
- **Email settings** (Account page, admins only): `GET /api/email/status` (server, port, SSL, sign-in, sender, APP_URL, "App password: Set" — never the value —, sent/waiting/failed since start, last error) and "Send test email to <me>" (`POST /api/email/test`) showing "Sent" or the exact reason.

### History

- `#/history` and `GET /api/history` (filters `person`, `team`, `status`, `from`/`to` on the creation date; `?format=csv` = CSV with UTF-8 BOM, CRLF, formula-injection guard). One row per request (with its linked task's people and dates) and one per task that isn't a request's task. Submitted date = latest "Submitted for approval" update; approved date = latest "Approved" update (or completion time for a direct completion); completed date = `completed_at` for tasks, `closed_at` (received) for requests; send-back reasons = all "Sent back: …" updates.
- Visibility: managers/admins everything; leads = their `taskScope` tasks + requests for their teams, made by their members, made by them, or whose task they can see; employees = tasks they're assigned + requests they made or whose task they did.

- **users.protected** (0/1, default 0): protected account (see "Owner and protected accounts"); added with `ALTER TABLE`, which set it once for deepith@hifocuscctv.com.
- **account_events**: id, user_id → users (cascade), actor_id → users (SET NULL; empty for server events), action (`owner_transfer`, `owner_refused`, `protected_refused`, `protection_on`, `protection_off`), detail ("<who> tried to …", "Owner changed from A to B …"), created_at. A person's account activity, index on user_id. Read with `GET /api/users/:id/events`.
- **login_failures**: email (lowercased), at. One row per failed sign-in; rows older than a day are dropped. **login_locks**: email (PK), locked_until. Account lockout (Security A1, backup `../backups/taskdesk-before-security-a1-2026-10-31.*`).
- **app_settings**: key (PK), value. `owner_user_id` = the owner at the last start (empty = nobody), used to notice and record a change of owner.
- **password_tokens**: id, user_id → users (cascade), token_hash (SHA-256, unique), purpose (welcome|reset), created_by → users (SET NULL), created_at, expires_at, used_at. "Set your password" links; the token itself is never stored.
- **sessions**: token (PK), user_id → users (cascade), expires_at, last_active_at (idle sign-out; added with `ALTER TABLE` in Security A1, older rows empty until their next request)
- **projects**: id, name, description, status (active|on_hold|closed), created_by → users, created_at
- **project_teams**: project_id → projects (cascade), team_id → teams (cascade); primary key (project_id, team_id). A project's teams (team tabs); none = "No team". Added for team tabs, backup `../backups/taskdesk-before-team-tabs-2026-10-28.*`.
- **tasks**: id, title, description, project_id → projects (SET NULL), assignee_id → users, assigned_by → users, priority (low|medium|high|urgent), status (assigned|in_progress|submitted|completed), progress (0–100), start_date, deadline, completed_at, submitted_at, approved_by → users, created_at, updated_at, deleted_at, deleted_by → users (SET NULL), archived_request_id → requests (SET NULL) — the last three added with `ALTER TABLE` for archiving (backup `../backups/taskdesk-before-archive-2026-10-27.*`), assignment_group_id (the copies of one multi-person assignment; the first copy's id, no foreign key; added with `ALTER TABLE`, backup `../backups/taskdesk-before-assignment-groups-2026-10-29.*`). Indexes on assignee_id, project_id, assignment_group_id.
- **task_updates**: id, task_id → tasks (cascade), user_id → users, message, progress, status, created_at, note_kind (`note` when posted with a message, `files` with files only, else empty; set by `POST /api/tasks/:id/updates` incl. group copies; drives note notifications; added with `ALTER TABLE` in 1.0.16, older rows empty). Activity log: progress posts, status changes, assignment/reassignment/deadline notes. Index on task_id.
- **teams**: id, name (unique, NOCASE), lead_id → users (SET NULL; compatibility only, kept equal to the first row of `team_leads`), created_at. "R&D", "Testing", "STQC Documentation" are created once, when the table is first created.
- **users.team_id** → teams (added with `ALTER TABLE`).
- **requests**: id, title, description, needed_by, requested_by → users, target_team_id → teams (SET NULL), status (validated in server.js), task_id → tasks (SET NULL), created_at, delivered_at, closed_at, reminded_at ("still unassigned" reminder sent; added with `ALTER TABLE` in 1.0.11, backup `../backups/taskdesk-before-team-blocks-2026-10-27.*`), asked_person_id → users (SET NULL; set for "Ask a person", cleared on give back/reassign) and withdrawn_from_id → users (SET NULL; who had it when the requester withdrew it), deleted_at and deleted_by → users (SET NULL; archived, added for archiving) — both added with `ALTER TABLE` in 1.0.12, backup `../backups/taskdesk-before-team-connections-2026-10-27.*`.
- **request_events**: id, request_id → requests (cascade), user_id → users, message, created_at. Request activity ("Sent to <team or person> by <name>", "<name> gave the request back", "<name> withdrew the request").
- **team_leads**: team_id → teams (cascade), user_id → users (cascade), added_by → users (SET NULL), added_at; primary key (team_id, user_id). Several equal leads per team; filled once from `teams.lead_id` when the table was created (backup `../backups/taskdesk-before-multi-leads-2026-10-28.*`).
- **team_managers**: team_id → teams (cascade), user_id → users (cascade), added_by → users (SET NULL), added_at; primary key (team_id, user_id). The teams a `team_manager` manages (see "Team managers"). `team_powers` is a TEMP view (per connection, not stored) = team_leads ∪ team_managers.
- **team_connections** (1.0.12): team_a_id, team_b_id → teams (cascade), created_by → users (SET NULL), created_at; primary key (team_a_id, team_b_id), `CHECK (team_a_id < team_b_id)`.
- **files**: id, original_name, stored_name (random, unique), size, mime (from the content, `sniffFile`), uploaded_by → users, task_id → tasks (cascade), update_id → task_updates, request_id → requests (cascade), created_at, message_id → messages (cascade; chat attachments, added with `ALTER TABLE` in 1.0.14, backup `../backups/taskdesk-before-chat-2026-10-28.*`). A shared assignment file has no task_id/request_id/message_id; it is reached through `task_files`.
- **task_files**: file_id → files (cascade), task_id → tasks (cascade), update_id → task_updates (SET NULL); primary key (file_id, task_id), index on task_id. Links one stored file to every copy of a multi-person assignment (see "Multi-person assignments").
- **conversations** (1.0.14): id, type (direct|group|team, validated in server.js), name (groups/teams), team_id → teams (SET NULL; unique for type team), created_by → users (SET NULL), created_at, last_message_at, archived_at (team deleted).
- **conversation_members**: conversation_id → conversations (cascade), user_id → users (cascade), joined_at, last_read_message_id, muted, is_admin (0/1, made a group admin; added with `ALTER TABLE`); primary key (conversation_id, user_id).
- **messages**: id, conversation_id → conversations (cascade), sender_id → users (SET NULL), body, created_at, edited_at (unused), deleted_at, system (0/1, a system line like "X added Y"; added with `ALTER TABLE`).

## Desktop app (Electron, Windows and Ubuntu)

- Source lives in `../desktop` (sibling folder of `server/`; dependencies not installed yet — run `npm install` there only when needed).
- Notifications (compared with the previous check; last statuses are stored in `config.json` as `knownStatuses` / `knownApprovalIds`): approver gets "<name> submitted '<task>' for approval"; the employee gets "'<task>' was approved" or "'<task>' was sent back: <reason>"; team members get "New document request for <team>: <title>", every lead of the team gets "New request for <team>: <title> – assign it to someone"; the leads and managers/admins get "Still unassigned: <title>" once per request (`knownReminderIds`, only grows, max 500); the requester gets "<title> is ready"; managers/admins get "New request needs a team: <title>" (`knownNeedsTeamIds`); a person asked directly gets "<requester> asked you: <title>" (opens the task) instead of "New task assigned"; every lead of their team gets "<requester> (<team>) asked <person>: <title>" (`knownAskIds`); the assignee (or the assigner, when the assignee posted) gets "<name> added a note to '<task>'" or "<name> sent files to '<task>'" (1.0.16, from `task_notes`, opens `#/tasks/<id>`; more than 3 at once become "n new notes and files on your tasks"; `knownNoteIds`, only grows, max 500, an older config.json records them silently first); the person and their lead get "<requester> withdrew: <title>" (`knownWithdrawnIds`; both lists only grow, max 500, and an old config.json records them silently first) (request notifications open `#/requests/<id>`; tracked as `knownRequestIds` / `knownReadyIds`). Each one waves the mascot. Badge = own open tasks + tasks waiting for the user's approval + open requests for teams the user leads (`assign_requests`) + for managers/admins requests without a team (`needs_team_requests`).
- **Chat (1.0.14):** the main process also keeps `GET /api/stream` open (`startStream()` after each summary check, with the session cookie; reconnects 2 s → 60 s back-off; logged as `[stream] connected/disconnected`). A `message` event notifies "<sender>: <preview>" (direct) or "<sender> in <chat>: <preview>", or "<sender> sent a file"; several within 3 s become one ("3 new messages in <chat>"); clicking opens `#/chat/<id>`. Tray/icon "Refresh" also reloads the dashboard. Floating icon: drawn on a fixed 104×104 stage scaled to the window, badge reserved inside the top-right corner, page zoom locked to 100%; every render logs `[widget] badge "…" at x,y WxH in IWxIH page (device scale …)` when it changes, with `OUTSIDE THE WINDOW` if it doesn't fit.
- **Mascot on every workspace and on top (1.0.15).** Only the floating icon; the dashboard stays a normal window. `keepWidgetUp()` re-applies `setAlwaysOnTop(true, 'screen-saver')` and (Linux) `setVisibleOnAllWorkspaces(true, {visibleOnFullScreen: true})` after every show, move, display change, blur and every 2 s (Linux also `moveTop()`); never while quitting/updating, never focusing. On X11 the workspace call only works after the window is mapped (calling it at creation is what left 1.0.14 on workspace 1 only). Linux window type `dock`: GNOME keeps it above "always on top" windows and doesn't hand it the focus when another window closes ('normal', 'toolbar' and 'notification' did); not `focusable: false`, which Electron turns into an unmanaged override-redirect window. Startup logs `[widget] shown: … _NET_WM_STATE … _NET_WM_DESKTOP(CARDINAL) = 4294967295 … → on all workspaces` (via `xprop`). Windows: no public API for virtual desktops (`setVisibleOnAllWorkspaces` is a no-op there); topmost skip-taskbar tool window. Position: `cfg.widgetPositions[<monitor setup>]` (key = the monitors' bounds); on start and on `display-added/removed/metrics-changed` the mascot goes to the place saved for the current setup, stays where it is if that monitor still exists, else the primary monitor's bottom-right.
- Diagnostics: the tray menu and the icon's right-click menu start with disabled lines "TaskDesk <version>" and "Last check: <time> (<n> open)" / "Last check failed: <reason>". Every summary check is logged to `~/.config/TaskDesk/taskdesk.log` (Windows: `%APPDATA%\TaskDesk\taskdesk.log`) as `[summary] ok user=… open=… approvals=… badge=…` or `[summary] failed: <reason> (HTTP <status>)`.

### Automatic updates

- The server serves `server/updates/` publicly (no sign-in) at `/updates` (mounted into Docker as `./updates:/app/updates`, so no rebuild is needed to add versions; missing files give 404). The desktop app (electron-updater, generic provider, feed = the laptop's own server address + `/updates`) checks 1 minute after start and every 4 hours, downloads silently, then installs silently and relaunches. Update problems are only logged, never shown.
- **To release an update:** change the code in `../desktop`, bump `version` in `desktop/package.json`, run `npm run release` from `desktop/`. It builds Windows + Linux, copies the .exe, .blockmap, .AppImage, `latest.yml` and `latest-linux.yml` into `server/updates/`, copies the .exe and .AppImage into `installers/`, and deletes older versions. Laptops update within 4 hours. 
- **First-time install on Ubuntu:** run `sudo apt install libfuse2` once (AppImage needs it on Ubuntu 22.04+), copy the AppImage to `~/Applications`, `chmod +x` it, and run it once. After that it updates itself without a password.
- Windows: run `TaskDesk Setup <version>.exe` once; later versions update themselves.
